# Архитектура backend — Git Code Review

**Ответственный:** Ilya Denezhkin, `@denezhkinia` · Инженер 3.
**Редакция:** 16 сентября 2026 года. Структура — 12 разделов arc42. Изменение 2.3: навигация, идентификаторы и однозначная терминология; новые продуктовые возможности и таблицы не добавлены.

**Порядок чтения для разработчика и AI:** сначала этот файл; для моделей — нужные `DB-*` в [схеме](docs/DATABASE_SCHEMA.md#schema-map); для фоновых действий — нужные `REC-*` в [восстановлении](docs/QUEUE_RECOVERY.md#recovery-map). Номер версии комплекта должен совпадать. Старые редакции — история, не параллельные требования.

**Владение правилами:** этот документ определяет поведение; `DATABASE_SCHEMA.md` — имена, поля, допустимые состояния и ограничения хранения; `QUEUE_RECOVERY.md` — порядок исполнения и восстановления. Диаграммы иллюстрируют словарь, но не заменяют его. При противоречии зафиксировать конфликт, не выбирать удобную трактовку и не менять схему молча.

**Статусы:** `confirmed` — требование пользователя; `proposed` — проектное решение для согласования; `open` — решения нет. Все документы описывают проект, не выполненный код. `RQ-*` — обязательные требования к реализации предлагаемой спецификации; её неподтверждённые настройки не становятся согласованными автоматически. Примеры не вводят новые поля или правила.

<a id="goals"></a>
## 1. Введение и цели

Пользователь подключает GitHub-репозиторий, выбирает профиль и перспективы, запускает ревью Pull Request и получает обоснованные замечания. Продукт многопользовательский; предусмотрены месячный доступ и покупка одного ревью.

Приоритеты качества: защита приватного кода, безопасные повторы, конечный расход ресурсов, проверяемые замечания и понятный небольшой команде код. Пользователь утверждает продуктовые условия; backend-команда отвечает за реализацию и тесты; эксплуатация — за лимиты и восстановление.

<a id="scope"></a>
## 2. Ограничения

| ID | Статус | Ограничение |
|---|---|---|
| SCOPE-01 | confirmed | Python, FastAPI, SQLAlchemy 2.x, PostgreSQL, Alembic, Ollama SDK; uv, Ruff, Pylint; Hexagonal |
| SCOPE-02 | confirmed | GitHub — Git-провайдер; GitLab не реализуется параллельно |
| SCOPE-03 | confirmed | Выбор платёжного провайдера пользователем из работающих вариантов для конкретной покупки |
| SCOPE-04 | confirmed | Профиль `default`, пользовательские профили; перспективы `general`, `frontend`, `backend`, `qa`, `po`, `devops`, `security` и пользовательские; отдельные промпты и запуски |
| SCOPE-05 | open | Модель LLM, языки, размер проектов, численные лимиты и коммерческие исходы — раздел 11 |

Stripe и Ziina — кандидаты, а не подтверждённые готовые интеграции. Реальный выбор требует минимум двух доступных вариантов для соответствующей покупки. Криптовалюта, промокоды, рефералы, микросервисы, отдельный брокер и векторная БД не добавляются автоматически. Python-парсер — кандидат, не обещание поддержки всех языков.

<a id="context"></a>
## 3. Контекст и границы

```text
Frontend → FastAPI → Application → Domain
                         ├── PostgreSQL: данные, очередь и контрольные точки
                         ├── GitHub App: подключение, код, PR и комментарии
                         ├── Ollama: ограниченный контекст без секретов
                         └── PaymentGateway: выбранный провайдер
GitHub / платежи → проверенный webhook → Application
Worker → те же Application-сценарии
```

Frontend не читает БД, не задаёт цену и не получает Git-токены. Внешний API не входит в транзакцию PostgreSQL. Подпись webhook не заменяет проверку права автора события тратить квоту.

<a id="strategy"></a>
## 4. Стратегия решения

Один сервис с одним прикладным ядром. Входные адаптеры запускают сценарии; выходные реализуют хранение, GitHub, модель и платежи. Repository не вызывает LLM. Внутренние алгоритмы не требуют транспортных обёрток.

Порядок задаётся кодом: подготовить → проверить перспективы → объединить → завершить → опубликовать. `WorkItem` хранит фиксированную команду; `Comment` и `Payment` — отдельные намерения внешних действий. Принятый `ModelCall` — контрольная точка. Перспективы первоначально последовательны, но независимы по промптам и результатам.

<a id="components"></a>
## 5. Компоненты и модель данных

```text
src/code_review/
  domain/              # состояния и чистые правила
  application/         # сценарии, контекст, доступ и порты
  adapters/inbound/    # FastAPI, webhook, worker
  adapters/outbound/   # PostgreSQL, GitHub, Ollama, платежи
  bootstrap.py         # связывание реализаций
```

Порты: UnitOfWork и repositories, GitReader, CommentPublisher, ReviewModel, PaymentGateway. Имена сущностей в коде и словаре одинаковы.

|---|---|---|

| Запуск ревью | MergeRequest, ReviewRequest, ReviewJob, PerspectiveRun | [DB-12–DB-20](docs/DATABASE_SCHEMA.md#schema-map) |

<a id="runtime"></a>
## 6. Сценарии выполнения

| Сценарий | Вход и проверки | Атомарное локальное изменение | Продолжение |
|---|---|---|---|
| Подключение | Сессия SaaS, роль owner/admin, права GitHub; проверенные callback/setup | GitIntegration, разрешённый Repository, WorkItem индексирования | Worker строит индекс точного commit |
| Запрос ревью | Роль, RepositoryGrant, Git-доступ, ключ и право использования | ReviewRequest, снимок настроек, резерв, WorkItem | Ответ `202` после commit |
| Анализ | Подтверждённая ревизия, актуальные права, владелец и бюджет | Job; затем сохранённые входы/попытки и принятые контрольные точки | Модель вызывается вне транзакции |
| Смена PR | Проверенный сигнал, сериализованная сверка GitHub | Новый descriptor/epoch, `superseded` несовместимых незавершённых jobs | Прекратить новые допуски; попытаться отменить текущий запрос |
| Финализация | Актуальность, покрытие, обязательные перспективы, резерв | Исход Request/Job, результаты, Comment, единственное решение по резерву | Независимая публикация |
| Оплата | Owner/billing_manager, допустимый продукт/провайдер | Purchase с ценой; Payment с выбранным провайдером | Проверенное подтверждение выдаёт право один раз |

`ReviewRequest` — продуктовая операция; `ReviewJob` — одна её ревизия. Новый commit не переписывает старый job. Контекст вызова не меняется при retry. Повторное планирование опирается на устойчивые ключи, не создаёт новые копии работ. Детали неизвестных ответов — [REC-04–REC-08](docs/QUEUE_RECOVERY.md#recovery-map).

<a id="deployment"></a>
## 7. Развёртывание

Один образ, процессы API и worker; приватные PostgreSQL и Ollama. Сверка Git, исполнение модели и обработка внешних эффектов имеют независимые ограниченные циклы. Инференс не блокирует отзыв доступа. Статический разбор изолирован по времени и памяти.

Миграции — отдельный шаг выпуска. Нужны TLS, защищённые секреты, резервные копии и проверенное восстановление. После восстановления БД внешние эффекты сверяются до повторных отправок. Последовательность и ограниченный JSONB-индекс расширяются по измерениям, не заранее.

<a id="rules"></a>
## 8. Сквозные правила

### 8.1. Реестр требований

Каждый `RQ-*` определяется только в этой таблице. Приложения ссылаются на ID и конкретизируют реализацию.

| ID | Требование |
|---|---|
| RQ-01 | Импорты направлены `inbound → application → domain`; `outbound → application.ports`. В ядре нет FastAPI, SQLAlchemy или SDK; репозитории не делают скрытых commit |
| RQ-02 | Для кода нужны активное членство/сервисный субъект, разрешение роли, RepositoryGrant и актуальный Git-доступ. Вложенные связи сохраняют tenant и нужного родителя; оплата не даёт доступа к коду |
| RQ-03 | Ревизия job, конфигурация запроса, PromptVersion, готовый RepositoryIndex и вход ModelCall фиксированы. Новый вход — новый логический вызов; новый commit — новый job |
| RQ-04 | После commit подтверждённой новой ревизии или отзыва доступа запрещены новые допуски и принятие старых результатов. Поздний ответ/потерянный lease не обходят запрет; удалённая отмена — по возможности |
| RQ-05 | Один ключ и то же тело возвращают прежнюю операцию; другое тело — `409`. Предметное изменение и следующий сохраняемый шаг атомарны; внешнего вызова внутри транзакции нет |
| RQ-06 | Принятие проверяет действующий token, срок, права, epoch, родителей и неизменный вход. У ModelCall один accepted_attempt; успешная контрольная точка не исполняется повторно |
| RQ-07 | Timeout/потеря commit-ответа означают неопределённость, не доказанный отказ. Неизвестный POST сначала сверяется; исчерпание retry не разрешает слепую отправку |
| RQ-08 | Окончательный вход + резерв генерации + запас помещаются в проверенное окно. Общий бюджет включает перспективы, синтез и повторы; неизвестный расход не обнуляется |
| RQ-09 | Payment фиксирует провайдера; незавершённая/неизвестная оплата блокирует следующий checkout заказа. Purchase выдаёт право один раз; резерв Request завершается только consumed либо released |
| RQ-10 | Секреты не попадают в контекст, браузер и логи. Код/промпты/комментарии — недоверенные данные. Webhook проверяется до применения; installation token не обходит недостаточные права пользователя |

### 8.2. Пользователи и роли — предлагаемая матрица

Роль хранится в `Membership`, не в `User`. Grant ограничивает ресурс, но не повышает роль.

| Роль | Разрешено | Ограничение |
|---|---|---|
| owner | Владение, роли, настройки и оплата workspace | Нет автоматического доступа к чужому GitHub-коду |
| admin | Действия member, подключения и профили, управление member/viewer | Нет назначения owner/admin/billing_manager и оплаты |
| member | Чтение, запуск доступных ревью, отмена своего активного запроса | Нет чужих ресурсов, управления доступом и оплаты |
| viewer | Чтение доступных результатов | Нет запуска, отмены, публикации и оплаты |
| billing_manager | Покупки, выбор провайдера, счета, подписка | Нет кода, findings и запуска ревью |

Owner/admin отменяют работы доступного репозитория. Последний активный owner защищён транзакцией; приглашение одноразовое, роль задаёт приглашающий. Бот — отдельный ServiceAccount с грантами, не admin. Статус матрицы — `proposed`, см. OPEN-07.

### 8.3. Контекст и внешние эффекты

Чанки: символ → diff hunk → ограниченное окно. Backend отбирает зависимости, тесты и DRY-кандидатов; весь репозиторий модели не передаётся. Индекс принадлежит commit; успешно завершённый job связывает принятый результат конкретного PR с этим индексом. Общего изменяемого графа всех веток нет.

Варианты оплаты определяет сервер по продукту, валюте и реальным возможностям. Закрытие браузера не отменяет Payment. Неопределённое предыдущее списание блокирует смену провайдера. Смена провайдера автоподписки — отдельный процесс. Деньги, права и расход модели не смешиваются; политика частичного результата остаётся открытой.

<a id="decisions"></a>
## 9. Архитектурные решения

| ID | Статус | Решение / цена |
|---|---|---|
| DEC-01 | confirmed | Hexagonal, один backend; единая БД сохраняет локальную атомарность |
| DEC-02 | confirmed | GitHub и выбор работающего платёжного провайдера |
| DEC-03 | proposed | WorkItem и предметные намерения; отказ от универсального EventDispatcher — пересмотр ADR-002, требует согласования |
| DEC-04 | proposed | Последовательные перспективы и ограниченный JSONB-индекс; масштабирование после измерений |
| DEC-05 | proposed | Фиксированные роли и RepositoryGrant; без конструктора политик |

Ни наличие интерфейса, ни диаграмма не доказывают надёжность. SQL-протокол проверяется на PostgreSQL. В этой редакции не меняются таблицы, права или состав MVP; уточняется способ чтения спецификации.

<a id="quality"></a>
## 10. Требования к качеству и приёмка

| Проверка | Правила | Проверяемый результат / тесты |
|---|---|---|
| Импорт инфраструктуры в ядре | RQ-01 | Проверка импортов отклоняет зависимость |
| Чужой tenant, ошибочный grant, отзыв доступа | RQ-02, RQ-04 | Нет запрещённого запуска/выдачи/принятия; AU01–AU10 |
| Retry, старый worker, новая ревизия | RQ-03–RQ-06 | Один разрешённый результат; QR01–QR06 |
| Потерянный POST/commit, восстановление БД | RQ-07 | Сверка вместо слепого повтора; QR03, QR07–QR08, QR13, QR15 |
| Unknown payment, два checkout, consume/release | RQ-09 | Одно право и один итог резерва; QR09–QR14 |
| Переполнение контекста, ошибка перспективы | RQ-08 | Нет скрытой обрезки и ложного полного успеха |

`AU*` определены в [схеме](docs/DATABASE_SCHEMA.md#access-tests), `QR*` — в [восстановлении](docs/QUEUE_RECOVERY.md#recovery-tests). Модель/промпт проверяются эталонными PR. Тесты не объявляются пройденными без запуска.

DoD задания: документ, физическая ERD, SQLAlchemy-модели, Alembic-миграция и PostgreSQL-тесты. Сейчас подготовлена только спецификация с проектными ER-диаграммами; код, полная DDL и миграции не созданы.

<a id="open-decisions"></a>
## 11. Риски и открытые решения

Неизвестное не заменяется придуманным значением. Блокируется только зависящая от него возможность; другие части и тесты можно разрабатывать.

| ID | Статус | Что требуется / когда |
|---|---|---|
| OPEN-01 | open | Модель, токенизатор, шаблон — до производственного инференса |
| OPEN-02 | open | Языки и размеры проектов — до обещаний покрытия |
| OPEN-03 | open | Бюджеты, heartbeat, backoff, timeouts, сроки — до допуска соответствующей работы |
| OPEN-04 | open | Активные платёжные адаптеры, валюты, продление — до checkout |
| OPEN-05 | open | Частичный результат, отмена и возвраты — владелец продукта до платного запуска |
| OPEN-06 | open | Принять DEC-03: изменение прежнего решения об EventDispatcher |
| OPEN-07 | open | Утвердить матрицу ролей, хранение и отзыв доступа — до приватного выпуска |
| OPEN-08 | open | Порог качества и допустимые задержки — по измерениям |

Очередь и восстановление описаны, но не испытаны. JSONB и последовательность имеют пределы памяти/задержки. При конфликте правил указать ID, затронутую операцию и вопрос; не возвращать удалённые сущности старых версий без решения команды.

<a id="glossary"></a>
## 12. Глоссарий

| Каноническое имя | Значение; что не следует создавать вместо него |
|---|---|
| Workspace / tenant_id | Область данных; `tenant_id = Workspace.id`, не отдельная таблица Tenant |
| User / Membership | Человек / роль в конкретном workspace; не глобальная роль User |
| MergeRequest | Внутреннее имя GitHub PR; не вторая таблица PullRequest |
| ReviewRequest / ReviewJob | Продуктовая операция / одна ревизия этой операции |
| ModelCall / InferenceAttempt | Неизменный логический вызов / его техническая попытка |
| state / phase | Поле состояния / шаг процесса; слово «статус» в тексте не вводит поле status |
| lease_token / owner_token | Текущее владение работой / token, зафиксированный у попытки; не Git access token |
| Unknown | Исход неизвестен; точные значения state определены в словаре, не новый общий enum |
