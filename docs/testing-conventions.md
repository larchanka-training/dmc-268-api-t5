# Соглашение по написанию unit-тестов

## Инструменты

- Фреймворк: `pytest`.
- HTTP-тесты: `fastapi.testclient.TestClient` (требуется `httpx`).
- Мокирование: `unittest.mock` (или `pytest-mock`), моки — только на внешних границах (сеть, БД, сторонние API).

## Расположение и наименование файлов

- Все тесты — в каталоге `tests/` в корне репозитория.
- Тесты одного модуля `main.py` — в `tests/test_main.py`; правило: имя тестового файла = `test_<имя_модуля>.py`.

## Наименование

- Тестовые функции — публичные, без классов-обёрток.
- Имя теста: `test_<что_делаем>_<ожидаемый_результат>`, например:
  - `test_health_returns_ok`
  - `test_root_returns_welcome_message`
  - `test_validate_mr_rejects_empty_title`
- Имя должно описывать ожидаемое поведение так, чтобы падение теста было понятно без чтения тела.

## Структура теста (AAA)

1. **Arrange** — подготовка входных данных и фикстур.
2. **Act** — один вызов тестируемого кода.
3. **Assert** — проверка результата; для HTTP — и `status_code`, и тело ответа.

## Что обязательно покрывать

- Золотой путь: сценарий, который проходит валидацию/возвращает успех.
- Для каждого правила валидации — минимум один сценарий, который его ломает.
- Граничные значения: пустые строки, `None`, пустые коллекции, неожиданные типы, очень длинные строки.
- Коды ошибок: проверяется конкретный `status_code` и тело ошибки (не только «4xx»).

## Чего не делать

- Не мокать то, что можно проверить интеграционно (реальный роутер, реальную функцию).
- Не проверять детали реализации (приватные вызовы, порядок внутренних шагов) — только наблюдаемое поведение.
- Не зависеть от порядка выполнения тестов и внешнего состояния; каждый тест самодостаточен.
- Не добавлять параметры `time.sleep` для синхронизации.
