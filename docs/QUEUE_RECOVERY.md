# Очередь и восстановление — приложение к v2.3

**Назначение:** конкретный протокол без нового брокера или универсального движка процессов. Это проект реализации, не отчёт о пройденных тестах. Область — WorkItem, ModelCall, Comment, Payment и WebhookInbox.


**Источник алгоритмов.** Поведение определяется [RQ-01–RQ-10](../BACKEND_ARCHITECTURE.md#rules). Поля и допустимые значения `state` берутся из [словаря БД](DATABASE_SCHEMA.md#schema-map); этот протокол не вводит альтернативные названия колонок или состояний. Таймауты и лимиты остаются [OPEN-03](../BACKEND_ARCHITECTURE.md#open-decisions), продуктовые исходы — OPEN-05. Описанные шаги ещё нужно реализовать и проверить.

`manual_required` есть у WebhookInbox; в остальных контекстах «нужен оператор» — описание действия, **не новое значение state**. Нельзя переносить состояние одного объекта в другой. `lease_token` принадлежит текущей работе; `InferenceAttempt.owner_token` фиксирует token допуска и не является пользовательским credential.

**Использование AI при реализации:** выберите REC, прочитайте связанные DB и требования, укажите эти ID в описании изменения и свяжите с QR/AU-тестом. Недостающий безопасный контракт провайдера — вопрос, а не основание выдумать recovery API. Операционные шаги ниже выполняются только по отдельной авторизованной команде; чтение документа не разрешает запускать платежи, повторные POST, SQL-исправления или миграции.

<a id="recovery-storage"></a>
## REC-01 · Что сохраняется

`WorkItem` — одна фиксированная команда: index_repository, resolve_review, run_review, sync_revision. Допустимые цели задаются явными FK и CHECK, а не произвольным именем класса в JSON. Долгое run_review последовательно исполняет вызовы и возобновляется с принятых ModelCall. PerspectiveRun не получает второй независимый механизм lease.

`Comment` и `Payment` опрашиваются как самостоятельные предметные намерения. У них свои поля владения для отправки/сверки. Нет дублирующей WorkItem-публикации на каждый Comment. WebhookInbox — входящая квитанция, а не сообщение, которому сразу доверены права.

Обязательные поля работы: business_key, state, attempt_count, max_attempts, available_at, lease_token, locked_until, deadline_at, last_error_code. max_attempts/deadline обязательны в производственном профиле; отсутствие значений не означает бесконечность.

<a id="recovery-claim"></a>
## REC-02 · Приём и получение

1. Входной HTTP/webhook проверяется. В одной транзакции сохраняются предметное изменение, идемпотентный ключ и необходимая работа. Успешный ответ только после commit.
2. Worker выбирает готовую запись с блокировкой `FOR UPDATE SKIP LOCKED`, повторно проверяет состояние и сроки, увеличивает номер владения/попытки, выдаёт новый token и срок. Транзакция завершается быстро.
3. До внешнего вызова отдельная короткая транзакция проверяет действующий token, права, текущий PR/epoch, родительский запрос и бюджет. Сохраняются окончательный payload, попытка и резерв вычислений. Получение работы не заменяет этот допуск.
4. Выполняется сетевой вызов. Ни SQL-транзакция, ни блокировка строки не удерживаются во время ожидания GitHub/Ollama/платежей.
5. Завершение принимается только тем же действующим владельцем. Один ModelCall имеет один accepted_attempt. Результат, его статус и следующий сохраняемый шаг фиксируются вместе.

SQL SKIP LOCKED используется для получения работы, а не как доказательство единственного внешнего исполнения [R1]. Два процесса могут физически вычислить ответ при потере связи; в БД принимается один разрешённый результат.

<a id="recovery-ownership"></a>
## REC-03 · Владение и отмена

Продление выполняется отдельной AsyncSession. UPDATE требует running, прежний token и ещё действующий срок. Проверка использует время PostgreSQL в точке проверки, а не часы worker. Потерянное право не продлевается задним числом. При неуспешном heartbeat worker прекращает новые действия и пытается отменить текущий запрос.

Порядок для транзакции исполнения: строка WorkItem/Comment/Payment как внешняя граница владения → workspace/членство/сервисный субъект → интеграция и репозиторий → PR → Request/Job/Call → ресурсы и Billing. Берётся нужное подмножество; однотипные строки сортируются по ID. Путь оплаты может брать только Payment и Billing. Путь оплаты не запускает ревью, уже удерживая Billing в обратном порядке.

Отзыв прав или сверка PR меняют авторитетный родительский запрет и не ждут старую WorkItem, удерживая MR/Workspace. Старые задачи отменяются логически через этот запрет, физически — позднее. Новый шаг создаётся вставкой с устойчивым ключом. Обновлять старую конфликтующую строку очереди «после MR» нельзя. Все ORM-запросы и скрытые FK-блокировки проверяются конкурентными тестами; перечисление порядка не заменяет тест.

Начатая короткая критическая секция держит свои блокировки до commit; lease не прерывает её физически посередине. Настраиваются пределы длительности транзакций. Для deadlock/serialization failure повторяется вся локальная транзакция с ограничением, а не уже выполненный сетевой вызов [R2].

Новая ревизия сохраняет descriptor, увеличенный revision_epoch и superseded незавершённых jobs атомарно. После commit запрещены новые допуски и принятие прежнего результата. Событие и массовая отмена детей не являются предварительным условием. Успешная историческая проверка не переписывается; она становится устаревшей. Отзыв доступа действует аналогично с access_epoch и проверкой текущих ролей.

<a id="recovery-classification"></a>
## REC-04 · Повтор или сверка: классификация

| Ситуация | Допустимое действие | Недопустимое предположение |
|---|---|---|
| Безопасное чтение GitHub не удалось | Отложенный повтор; учитывать Retry-After, deadline | 404 всегда означает удаление, а не отсутствие доступа |
| Получен rate limit | Backoff с jitter и сроком провайдера | Немедленно сменить token и продолжать |
| Неверный payload/нет permissions | Остановить соответствующее действие и запросить исправление | Повторять без изменения причин |
| БД не подтвердила commit | Перечитать logical/business key и принятый attempt | Нет ответа — значит commit не произошёл |
| Ollama не вернула полный ответ | Unknown attempt; консервативный расход; контролируемый повтор | Timeout освободил GPU и обнулил бюджет |
| Ответ GitHub POST потерян | Сверка публикации | Можно безусловно отправить снова |
| Ответ оплаты потерян | Сверка прежнего Payment либо разрешённый idempotent retry | Можно переключить провайдера |

Задержка определяется ограниченной экспонентой со случайным разбросом и Retry-After, где это применимо. Значения base/max delay, heartbeat и deadline выбираются после измерений. retry_count и unknown сохраняются независимо: исчерпание повторов не доказывает отсутствие внешнего эффекта.

<a id="recovery-inference"></a>
## REC-05 · Неизвестный результат Ollama

До отправки сохранены InferenceAttempt и неизменяемый ContextPayload. Полный ответ проверяется по формату и полноте. Часть JSON не считается успехом. При потере ответа попытка получает outcome_unknown; резерв ресурсов остаётся консервативным.

У Ollama в выбранном режиме может не быть подходящего сохраняемого ID запроса для последующего получения результата. В таком случае не выдумываем recovery API. Повтор допускается как новая техническая попытка того же ModelCall и того же payload, только если актуальны права/ревизия и осталось достаточно бюджета. Принятая попытка повторно не вызывается.

Истечение HTTP-timeout не доказывает прекращение вычисления. Endpoint с неопределённым активным запросом переводится в ожидание проверки: не выдавать неконтролируемые новые допуски. Возможные подтверждения — штатное окончание, проверенный механизм отмены выбранного сервера или контролируемое восстановление endpoint после прекращения других работ. Если такого подтверждения нет, требуется оператор; обычный health-check не доказывает отсутствие старого инференса. Жёсткий предел фактической удалённой работы возможен только при соответствующем серверном механизме, а не по одной локальной записи lease.

Поздний ответ может быть записан как диагностическое наблюдение расхода без принятия findings. Он не завершает потерявший владение ModelCall и не меняет актуальный итог.

<a id="recovery-publication"></a>
## REC-06 · Неизвестная публикация GitHub

Перед POST Comment сохраняется с `state=publishing` с publication_key, hash окончательного тела, точной ревизией/позицией и marker. После подтверждённого ответа сохраняется provider_comment_id. Crash после записи `publishing` даже до фактической отправки трактуется консервативно как неизвестность.

Сверка читает доступные страницы обсуждений, сравнивает marker, автора App, PR/commit и тело. Если найдено ровно соответствующее сообщение, локальное published фиксируется без нового POST. Несовпадение либо несколько объектов требуют разбора. Marker не является гарантией идемпотентности GitHub API.

Отсутствие объекта в ответе чтения — не доказательство, что ещё выполняющийся POST никогда не завершится. Новая отправка разрешена лишь после подтверждённого безопасного исхода по контракту адаптера. В остальных случаях состояние остаётся `delivery_unknown` и видимо оператору. Ручная команда «повторить» требует проверки и аудита, а не автоматически обходит этот запрет.

После изменения ревизии новый POST старого комментария запрещён. Read-only сверку прежнего POST можно закончить при действующем техническом доступе, чтобы учесть исторический эффект. Без доступа остаётся ожидание/операторское состояние. Нельзя объявлять удалённую публикацию транзакционно атомарной со сменой PR.

<a id="recovery-payment"></a>
## REC-07 · Оплата и выбор провайдера

Кнопки показываются по серверному списку capabilities для конкретного продукта/валюты/режима продления. Проверку нельзя ограничить UI: повторно проверить выбранный provider в CreateCheckout. Произвольный URL провайдера от клиента запрещён.

Purchase — один заказ с ценой/валютой/условиями. Payment — одна сохраняемая операция у конкретного провайдера. Безопасный сетевой retry остаётся тем же Payment с тем же request_hash и idempotency_key. Подтверждённая смена провайдера создаёт следующий Payment **того же заказа**; прежний не редактируется.

Правило: не более одного незавершённого Payment на Purchase. creating, pending, processing и payment_unknown считаются незавершёнными; требуется частичный уникальный индекс. Пока есть неизвестный исход, второй checkout запрещён. Закрытие браузера и локальное истечение TTL не доказывают отмену внешней оплаты.

Stripe поддерживает idempotency key, но хранение ключей ограничено: повтор после удаления ключа может создать новую операцию [R3]. Повтор с прежним ключом разрешается только в документированном безопасном окне и с теми же параметрами/аккаунтом/средой. После окна — GET/status/webhook-сверка или ручное решение, не слепой POST. Эти свойства не переносятся автоматически на Ziina: её create/get и контракт идемпотентности проверяются отдельно [R5].

Подтверждение проверяет provider account, environment, внешний объект, сумму, валюту и связь с нашим Payment/Purchase. Один webhook ID недостаточен: разные события одного платежа не должны повторно выдать Entitlement. Уникальность источника права и запись Purchase.fulfilled защищают второй бизнес-эффект.

Если всё же пришло два реальных подтверждения списания одного заказа, оба платежа сохраняются как факты. Право выдаётся один раз; лишнее списание переводится в разбор и при необходимости в отдельный идемпотентный возврат. Нельзя скрыть его UNIQUE-конфликтом и обещать, что второй внешний платёж невозможен.

Действующая Subscription сохраняет своего провайдера. Новый provider для следующего продления требует исключить двойное автосписание и согласовать период; в MVP такой перенос нельзя имитировать изменением поля. Автопродление и ручная оплата месяца остаются разными продуктами/режимами, пока не утверждено обратное.

<a id="recovery-settlement"></a>
## REC-08 · Резерв права и финализация

Один ReviewRequest имеет один UsageReservation. Reserve блокирует доступный остаток. Consume/release — один взаимоисключающий финальный переход. Новые ревизии при track_latest и технические retries используют тот же продуктовый резерв, но не обнуляют ресурсный бюджет.

Неуспешный результат требует явного FinalizeReview по утверждённой outcome policy. Не отпускаем резерв только потому, что work lease истёк: задача ещё может восстановиться. Если неизвестен внешний денежный платёж, не считаем его проваленным из-за deadline ревью. Review-finalization не делает повторное списание карты.

Commit с принятыми ссылками результатов, исходом Request/Job, решением по резерву и ограниченным набором Comment атомарен. Сетевых вызовов внутри нет. Повтор возвращает прежний итог. При новой ревизии раньше commit старый итог не принимается как актуальный; раньше завершённый итог остаётся историческим.

<a id="recovery-operations"></a>
## REC-09 · Периодическая сверка и инструкция оператора

Сканер независимо от событий проверяет: истёкшие lease; запросы без следующей задачи; jobs с готовыми контрольными точками; MR с requested_seq > applied_seq; неопределённые Comment/Payment; резервы завершённых запросов. Он вызывает те же сценарии с устойчивыми ключами, не выполняет прямые неконтролируемые исправления SQL.

Инструкция для проблемной записи:
1. Ограничить новые исходящие действия затронутой цели, сохранив чтение статуса и webhook.
2. Проверить логическую identity, token, parent state, эпоху доступа/ревизии и все внешние ID.
3. Получить авторитетное состояние провайдера и сохранённую контрольную точку; не интерпретировать timeout как отказ.
4. Выбрать разрешённое действие: признать прежний успех, продолжить чтение, повторить идемпотентную операцию, запросить восстановление доступа либо оставить неопределённый исход и передать оператору.
5. Выполнить аудируемой командой с прежней identity; не пересоздавать заказ/ревью ради обхода ограничения.

После восстановления БД из копии исходящие платежи и комментарии сначала приостановлены: провайдер мог выполнить больше действий, чем есть в восстановленной БД. Сверка должна охватить всё окно между точкой восстановления и остановкой прежних исполнителей.

<a id="recovery-tests"></a>
## REC-10 · Приёмочные тесты

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| QR01 | Crash до/после commit при приёме | Либо нет операции, либо Request и WorkItem восстановимы вместе |
| QR02 | Два worker одной задачи | Только один действующий token; поздний не меняет статус |
| QR03 | DB-deadlock после полного LLM-ответа | Повтор локального принятия без новой генерации |
| QR04 | Crash после принятого ModelCall | Продолжить со следующего вызова |
| QR05 | Новый PR/отзыв доступа при потерянном heartbeat | Старый ответ не становится accepted |
| QR06 | Запоздалый ответ сверки Git | Не откатывает revision_epoch |
| QR07 | Git POST принят, ответ потерян | Найти прежний комментарий; 0 новых POST при сверке |
| QR08 | Список Git пуст, POST ещё мог выполняться | Сохранить unknown, не доказанный отказ |
| QR09 | Два checkout одного Purchase | Один активный Payment; другой конфликтует |
| QR10 | Unknown Stripe и выбор Ziina | Второй provider заблокирован до безопасного решения |
| QR11 | Повтор разных событий одного платежа | Одно право и одна локальная выдача |
| QR12 | Подтверждения двух реальных платежей | Оба факта сохранены; одно право; сигнал о лишней оплате |
| QR13 | Просрочено окно idempotency провайдера | Нет слепого повторного POST |
| QR14 | Consume конкурирует с release | Один финальный исход |
| QR15 | Восстановление старой БД | Сначала сверка внешних эффектов, затем выдача работ |

Тесты не выполнены этим документом. Численные пределы heartbeat/backoff/timeouts утверждаются после выбора оборудования и нагрузочного измерения.

## Источники
