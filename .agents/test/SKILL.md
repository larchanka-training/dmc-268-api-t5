# Тестирование: workflow

Тестовый фреймворк — `pytest` + FastAPI `TestClient`. Полное соглашение (наименования, структура, обязательные кейсы, мокирование) — [docs/testing-conventions.md](../docs/testing-conventions.md); ниже — только шаги.

## Workflow: написать тесты для изменённого кода

1. Определи множество изменённых классов/функций: `git diff --name-only main...HEAD` (или диапазон, указанный пользователем).
2. Для каждого изменённого модуля определи/создай тестовый файл `tests/test_<имя_модуля>.py` по соглашению.
3. Для каждой изменённой функции напиши тесты, покрывающие обязательные кейсы из соглашения: золотой путь, сценарии провала каждого правила валидации, граничные значения, конкретные коды ошибок. Не переоткрывай соглашение — бери правила из документа.
4. Проверь, что имена тестов соответствуют шаблону `test_<что_делаем>_<ожидаемый_результат>` и структура AAA соблюдена.

## Workflow: запустить тесты

```bash
# Предусловие (однократно): зависимости тестов
pip install pytest httpx

python -m pytest                          # весь набор — основная команда
python -m pytest tests/test_main.py -v    # конкретный файл
python -m pytest -k <имя>                 # фильтр по имени
```

Диагностика падения: запусти только упавший тест с `-v`, прочитай assert-сообщение, воспроизведи входные данные вручную через TestClient. Если падение вызвано изменением поведения — сначала правь тест под новое поведение (см. соглашение), потом код.

## Критерий успеха

- `python -m pytest` завершается с кодом 0; вывод: `N passed`, 0 failed, 0 error.
- Каждый изменённый модуль имеет непустой `tests/test_<имя_модуля>.py`.
- Для каждого изменённого правила валидации существует минимум один «негативный» тест.
- Тесты не завязаны на порядок выполнения и не требуют сети/БД.

Если хоть один пункт не выполнен — workflow не завершён: исправь и перезапусти набор.
