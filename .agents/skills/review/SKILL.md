# Код-ревью: workflow

Критерии проверки (корректность, безопасность, тесты, стиль, градация замечаний Blocker/Should-fix/Nitpick) — [docs/code-review-checklist.md](../docs/code-review-checklist.md). Ниже — только процесс.

## Workflow: ревью PR

1. Получи изменения PR. Инструмент — на твоё усмотрение: если доступен MCP-сервер платформы хостинга репозитория (GitHub) — используй его инструменты для диффа/обзора; иначе CLI (`gh pr diff <номер>`) или локальный `git diff main...HEAD`.
2. Пройди по каждому файлу диффа все разделы чек-листа и зафиксируй находки с указанием: файл, строка, раздел чек-листа, серьёзность (Blocker / Should-fix / Nitpick).
3. Проверь тесты: для изменённой логики существуют тесты. Если скилл `test` доступен — прогони его workflow запуска, иначе запроси `python -m pytest` в CI.
4. Оставь замечания inline: через доступный MCP-сервер платформы хостинга либо CLI (`gh pr comment`); одна находка = один комментарий, привязанный к строке, если платформа это поддерживает.
5. Опубликуй итог в PR: сводка находок по серьёзностям и вердикт — тем же способом (MCP или CLI), каким публиковал замечания.

Не опирайся на конкретные имена MCP-инструментов — они меняются; при доступном MCP сам выбери подходящий вызов по его описанию.

## Вердикт

- `approve` — нет Blocker'ов (Should-fix и Nitpick допустимы, перечисли их).
- `changes requested` — есть хотя бы один Blocker.

## Критерий успеха

- Просмотрен каждый файл диффа (не выборочно).
- Каждая находка привязана к строке и к разделу чек-листа.
- Итоговый комментарий содержит явный вердикт (`approve` / `changes requested`).
- Все замечания опубликованы в PR (не только в чате).
