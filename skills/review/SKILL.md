# Код-ревью

## Чек-лист корректности

- **Логика валидации**: каждый добавляемый/изменяемый чек покрыт сценарием успеха и провала; результат корректен на граничных значениях (пустые поля, `None`, неожиданные типы).
- **Обработка ошибок**: входные данные валидируются на границе (Pydantic/схемы), генерируются осмысленные сообщения, а не голые 500.
- **Порядок выполнения проверок** детерминирован и задокументирован (если порядок важен).

## Безопасность

- Нет инъекций (SQL/команды/шаблоны) — см. OWASP Top 10.
- Нет захардкоженных секретов/токенов; конфиденциальные данные не попадают в логи и ответы.
- Валидация не выполняет опасных действий от имени пользователя без явного согласования (например, авто-апрув/мерж).

## Тесты

- Для изменённой логики есть тесты (см. `skills/test/SKILL.md`).
- Тесты проверяют поведение, а не детали реализации (чтобы рефакторинг их не ломал).

## Стиль и чистота

- Соответствие PEP 8 и типизации (аннотации типов на публичных функциях).
- Нет мёртвого кода, закомментированных блоков и избыточных абстракций.
- Имена переменных/функций отражают назначение.

## Как ревьюить через gitlab MCP

- Получить диффы/изменения: `mcp__plugin_gitlab_gitlab__summarize_merge_request_changes` (для быстрого обзора) или `list_merge_request_diffs`.
- Оставить inline-замечания: `mcp__plugin_gitlab_gitlab__create_merge_request_line_discussion`.
- Итоговый комментарий/апрув: `create_merge_request_note`.

## Итог

Ревью завершено, когда: логика корректна, безопасность соблюдена, тесты есть и зелёные, замечаний по стилю к мержу не осталось. Мелкие нитпики можно резолвить без повторов.
